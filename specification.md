# Техническое задание: Readme. Простой движок для блога

## О проекте

«Readme» — это простой headless-движок для блога, построенный с помощью микросервисной архитектуры и современного фреймворка Nest.js. Проект состоит из нескольких микросервисов, каждый сервис решает одну задачу.

## Общая концепция проекта

Вам предстоит разработать бэкенд для многопользовательского блога. Главная особенность сервиса — формат публикаций (их несколько) и возможность оформить подписку на обновления других пользователей. Подписка на пользователей влияет на контентную ленту пользователя.

## Технические требования

* Для разработки проекта применяется микросервисная архитектура. Студент самостоятельно определяет список микросервисов для приложения. Общее требование к сервисам: каждый сервис решает свою задачу.
* Некоторые сервисы могут содержать свою базу данных. Решение по выбору базы данных и её необходимость для определённого микросервиса остаётся на усмотрение студента. В приложении могут использоваться следующие СУБД: MongoDB, PostgreSQL.
* Для лучшего понимания работы проекта, студенту предоставляется полный набор вёрстки. Создавать из неё готовый фронтенд НЕ нужно. В рамках курса мы разрабатываем только бэкенд.
* В корневой директории проекта размещается файл `specification.md`. Файл содержит все необходимые инструкции для запуска проекта.
* Для разработки проекта используется актуальный LTS-релиз платформы Node.js. При необходимости студент может устанавливать дополнительные пакеты.
* Код сервисов разрабатывается только на TypeScript. Все сервисы размещаются в монорепозитории. Для построения монорепозитория используется NX.
* Техническое задание не определяет контракты и конкретные ресурсы разрабатываемого приложения. Решение по разделению приложения на сервисы, проектирование ресурсов API и другие архитектурные решения студент принимает самостоятельно.

## Функциональность

### 1. Регистрация и авторизация пользователей

* **1.1.** Регистрация доступна только анонимным клиентам.
* **1.2.** Для регистрации клиент передаёт следующий набор информации:
* *Электронная почта* (обязательно). Используется в качестве логина. Адрес уникален.
* *Имя пользователя* (обязательно). Фамилия и имя пользователя. Минимальная длина: 3 символа, максимальная 50 символов.
* *Пароль* (обязательно). Минимальная длина 6 символов, максимальная 12.
* *Аватар пользователя* (опционально). Ограничения: не больше 500 килобайт, формат `jpeg` или `png`.


* **1.3.** Перед записью выполняется процесс валидации. В случае ошибок полный список отправляется клиенту.
* **1.4.** Загруженные изображения для аватара могут храниться как в файловой системе, так и в базе данных.
* **1.5.** Приложение фиксирует дату регистрации пользователя.
* **1.6.** Пароль не хранится в открытом виде. Используется хеш (пакет `bcrypt`).
* **1.7.** При успешной регистрации возвращается корректный код состояния и объект с информацией о созданном пользователе.
* **1.8.** Авторизация построена на основе JWT. Возвращается токен с payload.
* **1.9.** Авторизованный пользователь может сменить пароль, передав текущий и новый (6-12 символов). Текущий пароль проверяется.
* **1.10.** Можно запросить детальную информацию по пользователю (по ID): дата регистрации, количество публикаций, количество подписчиков, уникальный ID.

### 2. Публикация постов в блоге

* **2.1.** Создавать, редактировать, удалять публикации могут только авторизованные пользователи.
* **2.2.** Пользователи могут редактировать и удалять только свои публикации (по ID).
* **2.3.** Удаление публикации приводит к удалению оставленных к ней комментариев.
* **2.4.** Виды публикаций: видео, текст, цитата, фото, ссылка.
* **2.5. Видео:** Название (20-50 символов), валидная ссылка на YouTube, теги (опционально).
* **2.6. Текст:** Название (20-50 символов), анонс (50-255 символов), текст (100-1024 символов), теги.
* **2.7. Цитата:** Текст цитаты (20-300 символов), автор цитаты (3-50 символов), теги.
* **2.8. Фото:** Фотография (до 1 МБ, `jpg`/`png`), теги.
* **2.9. Ссылка:** Валидный URL, описание (до 300 символов, опционально), теги.
* **2.10.** Автор определяется автоматически при сохранении.
* **2.11.** Автоматически сохраняется дата создания и дата публикации (можно редактировать в будущем для сортировки).
* **2.12.** Состояния публикации: «Опубликована» и «Черновик». По умолчанию — «Опубликована».
* **2.13.** Репост публикаций: копирование в свой список (один раз на публикацию). Меняется автор (оригинальный сохраняется), обновляется дата на текущую, фиксируется признак «Репост» и ID оригинала.
* **2.14.** Запрос детальной информации о публикации по ID (включая служебные флаги).

### 3. Список публикаций

* **3.1.** Список доступен всем. Возвращаются последние 25 публикаций разных авторов.
* **3.2.** Доступна пагинация (следующие 25 или остаток).
* **3.3.** Можно запросить публикации конкретного пользователя.
* **3.4.** Для публикаций пользователя действуют правила пагинации (3.1, 3.2).
* **3.5.** В список попадают только посты в статусе «Опубликовано».
* **3.6.** Сортировка:
* По умолчанию: Дата публикации (по убыванию).
* Лайки (по убыванию).
* Обсуждаемые / комментарии (по убыванию).


* **3.7.** Возвращаемые данные: тип, лайки, комментарии, дата, информация об авторе.
* **3.8.** Можно фильтровать список по типу публикации.
* **3.9.** Авторизованный пользователь может получить список своих «Черновиков».
* **3.10.** Недостающая в отдельном сервисе информация (только ID) может обогащаться на уровне API Gateway.
* **3.11.** Фильтрация публикаций по определённому тегу.

### 4. Моя лента

* **4.1.** Можно подписываться на других пользователей.
* **4.2.** Подписки формируют контентную ленту.
* **4.3.** В ленту входят и собственные публикации автора.
* **4.4.** Действуют общие правила сортировки и пагинации.
* **4.5.** Подписка осуществляется по ID пользователя.
* **4.6.** Есть возможность отписаться (материалы автора пропадают из ленты).

### 5. Лайки

* **5.1.** Доступно только авторизованным пользователям.
* **5.2.** Лайкать можно только посты в статусе «Опубликована».
* **5.3.** Один лайк на публикацию. Можно «забрать» лайк обратно.

### 6. Комментарии

* **6.1.** Доступно только авторизованным пользователям.
* **6.2.** Данные: Текст (10-300 символов), ID публикации.
* **6.3.** Автор и дата определяются автоматически.
* **6.4.** Можно удалять только свои комментарии (по ID).
* **6.5.** Список комментариев доступен всем (по умолчанию возвращается 50 штук).
* **6.6.** Доступна пагинация (следующие 50).

### 7. Уведомления на email

* **7.1.** Рассылка уведомлений о новых публикациях.
* **7.2.** Рассылается всем зарегистрированным пользователям.
* **7.3.** Письмо содержит список новых публикаций с момента последней рассылки.
* **7.4.** Оформление на усмотрение студента.
* **7.5.** Запуск рассылки осуществляется по запросу.

### 8. Поиск

* **8.1.** Доступен всем пользователям.
* **8.2.** Поиск по заголовку публикации (достаточно совпадения слов). Участвуют только опубликованные посты с названиями.
* **8.3.** Возвращается не более 20 публикаций.

### 9. API Gateway

* **9.1.** Отдельный сервис для подготовки данных для фронтенда.
* **9.2.** Объединяет ответы от разных микросервисов. Удобное место для выноса логики аутентификации/авторизации.

## Теги к публикациям

* Опциональны.
* Одно слово без пробелов, только в нижнем регистре (клиент может присылать в любом, сервер приводит к нижнему).
* Максимум 8 тегов на публикацию (больше — ошибка валидации).
* Дубликаты тегов игнорируются/удаляются автоматически.
* Начинается с буквы. Длина: от 3 до 10 символов.

## Документирование

* REST API сервисы документируются в формате OpenAPI с помощью встроенных средств Nest.js.

## Безопасность

* Конфиденциальная информация (пароли, секреты) не должна быть "зашита" в коде.
* Использование переменных окружения для секретов.
* SQL-запросы (если есть) должны быть параметризованными для защиты от инъекций.

## Необязательные задания

* Сценарий «Моя лента». Невыполнение не влияет на защиту по базовым критериям.
