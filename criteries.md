# Критерии качества проекта (Node.js / Nest.js)

---

## 1. Базовые критерии

### Работоспособность
* **Б1.** Код соответствует техническому заданию проекта. Все обязательные пункты ТЗ выполнены.
* **Б2.** При выполнении кода не возникает необработанных ошибок. Нет сообщений `error` и предупреждений о неправильном вызове методов или API. В пользовательском коде не используется deprecated API. Приложение не падает при любых сценариях использования, кроме предусмотренных спецификацией.

### Именование
* **Б3.** Название переменных, параметров, свойств и методов начинается со строчной буквы и записывается в нотации `camelCase` (исключение — перечисления, они пишутся в `PascalCase`).
* **Б4.** Для названия значений используются английские существительные. Сокращения запрещены, за исключением широко распространенных (`evt`, `ctx`, `i`/`j` для счетчиков, `cb`, `src`, `err`). Для предикатов допустима схема `is + признак`.
* **Б5.** Массивы названы существительными во множественном числе (исключение — слово `data`).
* **Б6.** Название функции или метод содержит глагол (исключения: функции-конструкторы и колбэки/обработчики).
* **Б7.** Названия констант (постоянных значений, известных до начала выполнения программы) написаны заглавными буквами в формате `UPPER_SNAKE_CASE`.
* **Б8.** Название классов, конструкторов и перечислений начинается с заглавной буквы (английские существительные). Значения перечислений (`enum` или `as const`) объявляются в формате `CamelCase`.

### Форматирование и внешний вид
* **Б9.** Используются обязательные блоки кода (фигурные скобки) для конструкций `for`, `while`, `if`, даже если инструкция однострочная (исключение — однострочные стрелочные функции).
* **Б10.** Список констант и перечислений идет перед основным кодом (в начале модуля).
* **Б11.** Код соответствует стилю оформления, принятому на проекте. Нет ошибок при проверке ESLint.

### Мусор
* **Б12.** В итоговом коде находятся только файлы из исходного репозитория, патчей или созданные по заданию. Нет неиспользуемого кода и закомментированных участков.
* **Б13.** В коде нет заранее недостижимых участков (невыполнимые условия, операции после `return` и т.д.).
* **Б14.** Журнал событий (логи) не сохраняется в системе контроля версий (для них должна быть отдельная директория в корне, добавленная в `.gitignore`).

### Корректность
* **Б15.** Константы нигде в коде не переопределяются и используются только для чтения.
* **Б16.** В названиях переменных и свойств не используются зарезервированные слова языка.
* **Б17.** Для определения ошибок используется только встроенный объект `Error` (`throw new Error(...)`).

### Модульность
* **Б18.** Название модуля соответствует содержимому, записано строчными буквами через дефис (например, `game-view.ts`) или с разделением пространств имен (`game.view.ts`). Экспорт и импорт производятся через `export` и `import`.
* **Б19.** Модули не экспортируют изменяющиеся переменные (используется `export const`).

### Оптимальность
* **Б20.** Своевременный выход из цикла: цикл не работает дольше, чем нужно.
* **Б21.** Количество вызовов циклов минимизировано (задачи решаются за один проход вместо нескольких, например, совмещая операции в `map`).
* **Б22.** Для работы с промисами используются операторы `async` и `await`.

### Безопасность
* **Б23.** Пароли не хранятся в открытом виде. В базе данных сохраняется только хеш пароля.
* **Б24.** В коде отсутствуют сохраненные реквизиты доступа (логины, пароли, секреты). Все конфиденциальные данные передаются через переменные окружения (`ENV`) или параметры командной строки.
* **Б25.** Отсутствуют операции записи в `GET`-методах. Они предназначены только для получения данных (исключение — сохранение статистики).

## 2. Дополнительные критерии

### Задача
* **Д1.** Техническое задание реализовано в полном объёме. Все обязательные и необязательные пункты технического задания выполнены.

### Корректность
* **Д2.** Название методов и свойств объектов не содержит название объектов.
  * *Неправильно:* `const popup = { openPopup() { ... } };`
  * *Правильно:* `const popup = { open() { ... } };`

### Избыточность
* **Д3.** Отсутствует дублирование кода: повторяющиеся части кода переписаны как функции или вынесены из условий (принцип DRY).
* **Д4.** Если при использовании условного оператора в любом случае возвращается значение, альтернативная ветка `else` опускается.
* **Д5.** Там где возможно, в присвоении значения вместо `if` используется тернарный оператор.
* **Д6.** Условия упрощены. Если функция возвращает булево значение, не используется `if..else` с лишними `return`.
  * *Правильно:* `return firstValue === secondValue;`
* **Д7.** Составные константы собираются в перечисления (`Enum`) или константный объект с модификатором `as const`.

### Магия
* **Д8.** В коде не используются «магические значения», под каждое из них заведена отдельная переменная, названная как константа (или элемент перечисления).

### Сложность и читаемость
* **Д9.** Для каждого события используется отдельный обработчик. Одна функция не является обработчиком нескольких разных событий.
* **Д10.** Длинные функции и методы разбиты на несколько небольших. Каждая функция решает ровно одну задачу (Single Responsibility).
* **Д11.** Для работы с JS-коллекциями используются специальные методы перебора массивов (`map`, `filter`, `sort`, `reduce` и прочие) вместо классических циклов, где это уместно.
* **Д12.** Оператор присваивания не используется как часть выражения (например, внутри вызова функций).

### Фреймворк Nest.js и архитектура
* **Д13.** Контроллеры остаются «тонкими». Детали реализации логики делегируются другим частям приложения (сервисам или пайпам). Контроллеры не должны содержать реализацию бизнес-логики и напрямую взаимодействовать с БД.
* **Д14.** Для структуризации кодовой базы применяется абстракция «Модуль» (`@Module`). Функциональность приложения разбивается по доменным областям, а не хранится в одном корневом модуле.
* **Д15.** Бизнес-логика реализуется исключительно в сервисах, внедряемых через паттерн Dependency Injection (DI).
* **Д16.** Для передачи данных между слоем представления (контроллером) и сервисом строго применяется паттерн DTO (Data Transfer Object).
* **Д17.** Отдаётся предпочтение встроенному набору объектов-исключений Nest.js (`NotFoundException`, `BadRequestException` и т.д.) вместо создания своих или использования общего `HttpException`.
* **Д18.** Валидация входящих данных реализуется в пайпах (`pipes`), а не внутри контроллеров.
